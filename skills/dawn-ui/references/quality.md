# 体验验收与精修闭环

本文为 dawn-ui 独立补充。检查按变更选取；不把全表变成每次任务的强制流程。

## 分开记录四种证据

- 视觉：当前版本真实截图，说明视口与状态，已实际查看。
- 交互：从真实入口操作，观察结果及恢复路径；录屏能说明过程，不能代替持久化断言。
- 工程：项目规定的检查和相关行为测试；构建通过不表示画面通过。
- 局限：尚未接入的服务、未测设备、无看图或运行能力；不要用分数覆盖缺口。

## 主流程验收表

| 改动涉及 | 至少验证 | 通过标准 |
| --- | --- | --- |
| 浏览与查找 | 查询、清空、无结果、返回 | 条件与位置可恢复，不误显示旧响应 |
| 编辑与提交 | 正常提交、校验失败、服务失败 | 成功对应真实结果，失败保留输入并可重试 |
| 持久化 | 保存后刷新、重新读取、保存失败 | 内容与状态一致，不能静默丢失或伪称保存 |
| 余额与次数 | 边界用尽、快速连按、失败 | 不重复结算，限制与提示对应真实规则 |
| 弹层与抽屉 | 键盘打开/关闭、Tab、Esc、焦点返回 | 不陷入无出口，不操作到背景，不丢草稿 |
| 响应式 | 桌面、窄屏、长内容、浏览器缩放 | 主任务完整，关键操作可达，没有裁切遮挡 |
| 动效或视觉特效 | 正向、逆向、快速中断、减少动态效果 | 状态稳定、内容完整，无动画依赖的业务结果 |
| 共享组件 | 代表性使用处及相关状态 | 修复没有造成同类页面退化 |

直接地址参数可帮助截状态图，但不能代替真实操作到达该状态。测试等待可观察条件，不用固定延时断言异步完成。已有稳定验证脚本优先复用；遇到真实偶发失败才重复运行并分析，不机械要求所有测试连跑三次。

## 精修顺序

1. 先解决流程阻断、数据丢失、误导成功和可读性。
2. 核对首屏主角与下一步是否清楚。工具以业务对象和任务为主角，不为新奇推翻高效布局。
3. 调整全页共同锚线、文字尺度、行距与密度；再修组件边缘和反馈。
4. 删除重复说明、无意义眉标、过量状态色、盒子和装饰；保留判断依据和操作上下文。
5. 再看记忆点是否还在，减少后主角是否更强；不能把设计统一磨成无特征的空白页。

“圆角”“渐变”“侧栏”并非本身错误。只有无产品依据、削弱层级或影响任务时才调整，避免把反模板检查变成另一套模板。

## 评审闭环

每轮按“位置 → 观察 → 影响 → 修改目标 → 验收方式”写问题，先最多五个主要问题。修正后逐项核对实际变化，不靠换措辞表示进步。

新设计评分同时看任务、可读性与视觉完成度，9 分表示主流程和异常状态已验证、至少一处达到品类优秀水准且剩余差距很小；不意味着客观认证。没有执行流程时只评视觉，并明说交互未验证。规范对齐的精修不打分。

默认一轮，重要差距尚存或用户要求精品打磨时最多三轮；同一方向连续两轮没有可见收益、预算用尽或偏好冲突时停止。审美停止不等于功能完成；必需流程未完成时在交付里明确影响与阻塞。

交付复用任务已有组织方式，简述做了什么、实际怎么验证、还缺什么。需要评审记录时写每轮依据、处理结果和保留项；不要把每项内部检查都塞进面向用户的回复。
